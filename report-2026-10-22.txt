## 4. Two real bugs found and fixed in the recovered code
1. **tool/gltf_to_glb.mjs reported the wrong world bbox.**
   The old `worldMatrix()` picked the last root node that had children and used
   its matrix for every primitive — right for this one file, wrong in general.
   While rewriting it to map each mesh to its own node matrix, the rewritten
   walk produced an *unrotated* bbox, which exposed the actual API trap:
   `Root.listNodes()` returns **every node flat**, not the scene roots, so
   nested nodes were re-rooted and their parent transform dropped. The walk now
   starts from `Scene.listChildren()` (and falls back to root-less nodes), and
   the bbox is back to the expected x[-1,8] y[0,16] z[-3,7] with the Z-up→Y-up
   rotation applied.
2. **viewer/src/main.js hard-coded the tulip twice**
   (`flower.procedural === 'tulip' || flower.id === 'tulip'`). Replaced with a
   `PROCEDURAL_BUILDERS` registry keyed by the catalog's `procedural` field,
   and the accent colour is now parsed with `parseInt(hex, 16)` instead of
   string-replacing '#' with '0x'.

## 6. Decisions
- Kept the model asset in the repo (rose.glb, 120 KB) — it is small, and it is
  the single source both renderers read. The 167 KB .gltf source stays in
  app/assets/models/source/ so the asset can be regenerated.
- The tool stays a Node script in tool/ (second toolchain, ~300 lines instead
  of ~200 lines of hand-rolled GLB/PNG code in Dart).
- Baking to COLOR_0 and deleting the palette texture stays the strategy: it
  works in both renderers, needs no sampler support (the flutter_scene build
  hook drops samplers), and avoids a 4-px palette cell turning to mush in the
  mip levels when the flower is small on screen.
